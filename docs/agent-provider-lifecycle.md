首批功能的实际交付范围、逐项模型回复及未通过原因见[实施验收](agent-provider-acceptance.md)。

## 产品决策

建议首批交付 **Codex、Claude Code、OpenCode 2.x、GitHub Copilot CLI**，先打通安装、原渠道更新、复检和跨机器任务恢复。四者都有近期独立社区参与，均完成了真实 Linux 用户级安装、前后版本检查和新版协议握手。具体开放单位是 **provider × 安装渠道 × OS × 架构**。一个 Linux npm 组合通过，不能替同名的 Windows 安装器或 Homebrew 安装背书。当前通过的是技术验证，正式写操作还需要下面的放行测试。

首批四项的 npm 渠道在 Linux arm64、Linux x86_64 用户空间和 macOS arm64 均完成真实升级和握手，各自 28 天包下载超过 300 万，且都有可查的近期公众参与。Qwen 同样通过三组技术验证，28 天约 61 万次包下载，可作为共用执行器的下一项。Qoder 则适合作为第一款原生安装器试点，直接覆盖当前设置页所遇到的桌面已装、CLI 待补场景。这里用下载量给已通过技术门槛的候选排序，不用它估计用户数。

| 可见范围 | Provider | 交付决定 |
|---|---|---|
| 首批候选 | Codex、Claude Code、OpenCode、Copilot CLI | 默认可安装列表。先放行完成验证的渠道。原生自更新与 Hermesh 定时更新只启用一个。Claude 原生升级实测未过，优先开放已验证 npm 渠道的手动更新；原生渠道需另行放行。 |
| 下一批，共用 npm 执行器 | Qwen Code、Kimi Code 2.x、CodeBuddy Code、Grok Build | 实测同渠道升级并握手。Qwen、Kimi 有可观的官方项目参与；CodeBuddy、Grok 的公开反馈口径不同。列入「更多工具」，按需求逐项开放。 |
| 下一批，原生渠道 | Antigravity、Cursor、Qoder、Goose、Kiro | 优先用厂商自更新。Antigravity、Cursor 已验证全新安装，Qoder 有实际用户场景且已验证原生双版本。Goose、Kiro 需要额外系统依赖和平台验证。 |
| 首版仅识别和使用 | Auggie、DeepSeek Harness、Gemini CLI | Auggie 可用但本次可比官方样本较小；DeepSeek 参与活跃，CLI 默认包仍为 RC；Gemini 个人账号已迁移，企业和付费 API 仍有用途。默认未安装列表收起这三项。 |

这份评估没有足够依据删除任何已有 driver。**可以现在裁掉的是首版安装承诺和默认入口**。已安装项、已有授权、默认模型、历史会话恢复继续按原 ID 工作。若将来彻底结束支持，先核对连续两个评审周期的社区变化、上游维护状态和可获得的 Hermesh 实际使用证据，再提供迁移说明。当前没有采集用户机器的使用量。Demo 中 Gemini 的版本和更新操作是交互示意，首发产品应换成上述首批工具。[Google 账号迁移公告](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/)

**复审规则**：每季度重取最近 90 天的参与证据。新入口优先进入测试队列的条件是至少一个直接社区来源显示多个独立参与者、有可验证的稳定分发、同一渠道已有跨版本样本。公开反馈较少时，应核查官方论坛、集成仓库和已有用户需求。只有上游明确终止支持，或连续两个稳定版本不能通过核心协议并且没有可维护的替代路径，才发起 driver 下线评审。品牌热度的涨跌只影响展示顺序和测试投入。

## 用户看到什么

- 在一台机器的设置中，已知来源的稳定版更新点一次启动。右侧原位显示「更新中」，副标题显示目标机最近回报的阶段。更新完成后替换版本。首次安装确认机器名、执行账户和来源。
- 机器上有该 provider 的活动会话时，手动选择「空闲时更新」只排这一次。长期策略从更新设置开启。已有固定版本、预览渠道、显式二进制覆盖以及用户关闭的厂商更新设置优先。
- 跨机器的「任务记录」按任务显示机器、provider、时间、阶段和结果。断线保留最后回报和时间。重新连接后查原任务。需要处理时，行内显示错误摘要，点开才展示处理建议、最近输出和可用动作。
- CLI 写入成功、握手成功、登录成功是三个独立事实。写入后验证失败显示「已安装，需复检」。握手成功但缺凭据显示「待登录」。登录仍在目标机器或厂商支持的设备授权流程完成。

## 安装来源与更新所有权

每条随版本发布的配方只描述已验证的 provider ID、平台组合、来源标识、固定包名或官方发布地址、可执行入口、先决条件、更新所有者和复检协议。第一版共用 npm 安装流程；原生安装器按厂商添加。版本检查限定同包、同主线、稳定发布标签且目标版本本身非预发布；不能只信 latest。ACP Registry 和上游每日握手报告可作为发现变化和选取候选版本的输入。审核后的固定版本和渠道随 Hermesh 配方发布。注册表里的 Claude/Codex ACP 包是桥接器，不能替换现有两个原生 driver。[ACP 分发格式](https://github.com/agentclientprotocol/registry/blob/main/agent.schema.json) · [上游协议矩阵快照](https://github.com/agentclientprotocol/registry/blob/72697f65e971719c0d4ea4e0d3d954ac5b81510a/.protocol-matrix/latest.md)

1. **先发现。** 解析 Hermesh 实际会启动的文件、真实路径、版本、来源凭据。同名二进制、shim 或 `--version` 不足以证明所属包管理器。npm 要从同一 Node/npm 前缀核对已安装包、版本和 bin 指向；Homebrew 要核对安装记录和链接。桌面内置副本归桌面应用维护。来源冲突时显示路径并提供官方说明。
2. **再安装。** 没有兼容安装时，目标机按真实 OS、CPU、Linux libc、运行时版本、目录权限和依赖做预检。npm 首版只支持已有且版本合适的 Node/npm；新安装落在每个 provider 的用户级专用前缀，记录包版本及已解析入口，并让 Hermesh 的发现和启动共用该入口。显式覆盖优先。官方原生安装器遵循自己的用户级目录。无需在远程桌面开终端，也不自动为用户安装 Node、Homebrew 或系统依赖。
3. **由原渠道更新。** Hermesh 自己安装并拥有的前缀可定时升级稳定版。用户原有的 npm 或 Homebrew 安装只有在能证明归属时才提供按原渠道手动更新；用户选择托管、渠道确实能控制更新时才开放空闲自动更新。厂商原生自更新显示「由厂商管理」，保留用户设置，只在能保证同一份二进制时提供厂商的更新动作。OpenCode 1→2、Kimi 1→2 等跨产品线迁移独立确认。
4. **验证并生效。** 写入前记录旧版本与路径；写入后用目标 daemon 的环境重解析，核对目标版本、渠道和协议握手，再刷新机器状态。该探测必须在本次写入后开始，不能加入写入前已启动的全局扫描。受管前缀可在独立版本目录验证成功后原子切换指针，保留上一份可用版本。外部包管理器由其自身决定回滚能力，失败后先检查目录与实际版本。

**多台机器共享 home 目录时**，本机空闲检查无法看到另一台机器的进程。受管安装优先使用机器本地磁盘和版本目录；不能确认前缀归本机独占时关闭自动写入和旧版本清理。Claude 官方特别指出，NFS 上替换或回收旧可执行文件可能让另一台机器的活动会话崩溃。对厂商管理安装显示该风险和原渠道，引导使用独立前缀。[Claude 网络存储说明](https://code.claude.com/docs/en/setup#install-on-network-storage)

**自动更新调度**：对主动选择 Hermesh 托管的组合，建议每台机器每日带随机延迟检查一次已审核的稳定版本，离线后在下次上线时合并补查。检查本身不启动交互式 CLI；比较包管理器记录、上次验证版本和渠道。命中时创建普通更新任务，使用同一空闲锁、复检和历史记录。人工取消当次版本、验证失败或来源发生变化时暂停该版本的自动重试，等用户处理或新的合格版本到来。用户撤销策略时撤销尚未写入的排队任务。厂商自更新只做发现和结果展示，遵循厂商的节奏与选项。

## 跨机器任务协议

拟增 `ProviderMaintenanceCapabilities`、`StartProviderOperation`、`ListProviderOperations`、`GetProviderOperation`、`ControlProviderOperation`。能力协商包含协议版本以及每项可执行动作和不可用原因。旧 daemon 返回未实现时，设置页退回现有识别与使用能力。远程安装、更新策略和取消请求只接受有该机器管理权限的 owner；项目、会话和普通 agent grant 不可借此获得软件安装权限。

开始请求带 `machine_id, provider_id, action, request_id, expected_installation, expected_version`。最后两项用于防止点击后路径或版本已经变化。目标机在事务中写入操作、校验配方和幂等键，落盘后返回 `operation_id`。超时后 owner 使用同一 request ID 查询或重发；同 ID 不同参数返回冲突。客户端只传枚举和预期状态，执行文件、参数、下载域名和目标目录都由目标机解析。对相同机器、provider 和安装来源串行化写操作，共享包管理器前缀还要尊重其锁。

每条事件含 `operation_id, sequence, phase, timestamp, summary`。机器存储任务、最后序号、旧/目标版本、来源、尝试次数和有限长度的脱敏诊断。客户端从最后序号补拉，重复事件忽略。第一版在任务页或有活动任务时短轮询，离开页面任务继续，终态停止轮询。支持断线后查询；离线时新点击的安装默认不排队。在活动会话结束后再做一次互斥检查，防止更新与新会话启动同时进入。

| 目标机状态 | 动作和恢复语义 |
|---|---|
| 等待空闲／预检 | 可取消；检查平台、账户、磁盘、依赖和可写目录。持久化策略的等待任务可在重启后重新评估。 |
| 下载 | 仅在有可靠字节计数时显示百分比。否则显示阶段、最近回报与耗时。网络错误允许有界重试，超时从目标机计时。 |
| 写入 | 提交前锁定来源和路径。可控分阶段安装在写入前支持取消。第三方安装器把下载和写入合在一起时，只显示「安装器运行中」，从启动时起收回取消操作。 |
| 验证／成功 | 二进制可运行并完成相应握手后记录成功和实际版本。来源可写但握手失败保留「重新检测」，只验证已写入的文件。 |
| 失败／中断 | 权限、架构或来源不明需先修条件。远程连接丢失只改变本机的观察状态。目标 daemon 重启先对账安装器、锁、实际文件和版本，不能证明结果时标为「待核实」；禁止盲目重放写入。 |

首次只实现这条链路。把下载、签名或官方校验值验证、执行超时、有限重试、输出脱敏放在各适配器共用的执行层。安装进程用目标 daemon 的普通用户身份，在独立工作目录中运行；项目内容、模型密钥和 owner 私钥不作为安装参数。需要管理员权限、交互式 SSO 或企业策略阻止时，返回目标机可操作的下一步。

## 交付与验收

1. **先做一个完整组合。** 选 Codex npm + Linux，打通原型 UI → owner → 真实目标 daemon → 官方包 → app-server 握手 → 断线重查。两台测试机器上同时发起操作，核对事件、路径、版本和各自的任务 ID。
2. **扩展首批配方。** 同一执行层增加 Copilot、OpenCode、Claude。每个声明支持的系统和架构在干净普通用户环境完成全新安装、真实跨版本更新、未登录握手和幂等复检。Windows 使用原生 runner 检查 npm shim、PowerShell、文件占用和 PATH 生效；macOS 分测 app bundle、用户级 CLI 和 Homebrew 前缀。使用受控测试账号单独验证一次登录后的 Hermesh 会话。
3. **验证故障后才开放自动更新。** 覆盖请求已执行但响应丢失、重复点击、用户固定版本、活动会话竞争、磁盘满、网络或安装源掉线、包管理器锁、写入时 daemon 退出、升级后握手失败、跨设备取消、旧客户端/daemon 混用和权限拒绝。断线补拉只显示一条任务；任何失败都不能伪报「已是最新」。
4. **运维按组合收缩。** 定期检查官方稳定渠道变更，先在测试机滚动验证，再向选择自动更新的机器放行。协议或安装器回归时停用该组合的新安装／自动更新，保留发现、历史和官方指导。观察安装成功率、验证失败率、重试率和失败原因，按渠道和平台区分；人工取消、待登录和机器离线分别计数。首次小范围试用后再以有效样本设定目标，避免用本次单机实验承诺线上成功率。

本次实际跑过的组合、现有回归的失败项、尚缺的平台和验收项均列在[验证记录](agent-provider-evidence-2026-11-27.md)。实现预算主要取决于支持的平台和渠道组合数，而非列表中的品牌数。沿用机器路由、官方更新器和三种既有握手，才能让维护量随新增配方可控增长。
